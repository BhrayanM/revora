# Phase 14.6D Slack and Twilio Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver Slack OAuth plus HOT-lead notifications and add read-only, no-charge Twilio connection infrastructure.

**Architecture:** Pure provider-contract modules own validation, response parsing, error normalization, and signature verification. Server-only adapters own OAuth/API calls and encrypted persistence through the existing integration services. Slack notification orchestration runs after a successful HOT qualification; Twilio exposes no send operation.

**Tech Stack:** Next.js 16.3 App Router, React 19 server actions, TypeScript, Node crypto/fetch, Supabase/Postgres, Node assertion scripts.

**Spec:** `docs/superpowers/specs/2026-08-20-phase-14.6d-slack-twilio-design.md`

## Global Constraints

- Slack uses OAuth v2 and the `incoming-webhook` scope.
- Twilio sends no SMS, WhatsApp message, or voice call and performs no paid or mutating provider operation.
- Credentials remain encrypted and server-only; safe DTOs contain no token, Auth Token, or webhook URL.
- Every persistence operation is scoped by authenticated organization.
- Migrations `00001` through `00033` remain unchanged; no Phase 14.6D migration is expected.
- Provider calls use HTTPS, timeouts, bounded parsing, safe errors, and no redirects for webhook delivery.
- Implementation uses red-green-refactor and creates local commits only; no push or deployment.

never throws into the qualification flow.

Call it after successful qualification persistence in both qualification
services. The persisted AI result remains successful even if notification
returns `failed`.
