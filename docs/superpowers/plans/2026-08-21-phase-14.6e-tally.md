# Phase 14.6E Tally Integration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use
> superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use
> checkbox (`- [ ]`) syntax for tracking.

**Goal:** Connect one Tally form per organization through the Tally API and
turn each valid signed form submission into exactly one Revora lead.

**Architecture:** A pure Tally contract layer validates provider data, field
mapping, signatures, and payloads. A fixed-origin server adapter owns bounded
Tally API calls, while organization-authorized actions own connect/test/
disconnect lifecycle. A public route resolves a hashed routing token, verifies
the exact raw body, claims the event in the existing webhook ledger, and calls a
focused ingestion service.

**Tech Stack:** Next.js 16.3 App Router, React 19, strict TypeScript, Node
`crypto`, Supabase/PostgreSQL with RLS, Node assertion verification scripts.

**Spec:**
`docs/superpowers/specs/2026-08-21-phase-14.6e-tally-design.md`

## Global Constraints

- One selected Tally form per organization in Phase 14.6E.
- Use only `https://api.tally.so` and pin `tally-version: 2025-02-01`.
- Store the API key and signing secret only in encrypted server credentials.
- Store the 256-bit routing token only as a SHA-256 hash.
- Verify `Tally-Signature` with HMAC-SHA256 over the exact raw body before JSON
  parsing or persistence.
- Accept at most 1 MiB and persist no raw payload, unmapped answer, file URL,
  preview/PDF URL, or signature image.
- Scope every database lookup and event uniqueness boundary to organization.
- Do not modify migrations `00001` through `00033`; create `00034` with the
  Supabase CLI.
- Preserve all Phase 14.6B-14.6D provider behavior.
- No push, deployment, historical import, purchases, or paid provider action.
