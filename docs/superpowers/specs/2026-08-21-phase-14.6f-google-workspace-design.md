# Phase 14.6F Google Workspace Design

**Date:** 2026-08-21  
**Status:** Implementation-ready  
**Scope:** Google Calendar + Gmail only

## Goal

Add one organization-scoped Google Workspace authorization that enables a
strictly bounded Calendar operation and a strictly bounded Gmail operation,
while preserving Revora's existing authorization, encryption, tenant, audit,
and provider lifecycle contracts.

## Product Boundary

Phase 14.6F delivers:

- one Google identity per Revora organization;
- one OAuth consent flow that connects both Google Calendar and Gmail;
- encrypted offline credentials with coordinated refresh;
- read-only connection tests;
- coordinated remote revocation and local disconnect;
- a server-only operation to create a bounded appointment on the connected
  user's primary calendar;
- a server-only operation to send one bounded plain-text Gmail message;
- safe audit metadata for successful provider mutations.

It does not deliver the dashboard Calendar module, an inbox, message reading,
message tracking, bulk email, campaigns, templates, attachments, HTML mail,
calendar synchronization, webhooks, recurring events, conferencing, calendar
selection, or automatic invocation from an automation. Product surfaces for
Calendar and other remaining `Soon` modules stay in Phase 14.7.

## Approved Architecture

### One Google Workspace grant

Google Calendar and Gmail are presented as separate catalog cards because they
are separate capabilities, but they are one authorization bundle:

1. Connect from either card starts the same Google Workspace OAuth flow.
2. The OAuth state is organization-bound, actor-bound, expiring, single-use,
   and canonically bound to `google-calendar`.
3. The callback verifies one Google subject and email address.
4. Calendar and Gmail integration rows are written atomically in one database
   statement with the same encrypted credentials, subject, email, scopes, and
   expiration.
5. Tests and token refresh validate that both rows still represent the same
   identity. Drift fails closed and requires reconnection.
6. Disconnect from either card revokes the shared Google grant and disconnects
   both local rows.

The existing `integrations` table already supports the two providers and a
unique row per organization/provider. No new credential table is needed.

### Least-privilege scopes

The exact requested scope set is:

- `openid`
- `email`
- `https://www.googleapis.com/auth/calendar.events.owned`
- `https://www.googleapis.com/auth/gmail.send`

The broad `https://www.googleapis.com/auth/calendar` placeholder is removed.
No Gmail read, metadata, modify, compose, settings, labels, history, or mailbox
scope is requested. No Calendar ACL, calendar-list, settings, or unrestricted
calendar scope is requested.

The authorization request uses the fixed Google authorization origin,
`response_type=code`, `access_type=offline`, `prompt=consent`, and the exact
configured redirect URI. Previously granted scopes are not incrementally
included. The callback rejects a grant that omits any required scope or returns
an unexpected scope outside the exact allowlist.

Official references:

- <https://developers.google.com/identity/protocols/oauth2/web-server>
- <https://developers.google.com/workspace/calendar/api/auth>
- <https://developers.google.com/workspace/gmail/api/auth/scopes>
- <https://developers.google.com/identity/openid-connect/reference>

### OAuth endpoints and bounds

The server-only adapter may call only these fixed origins and paths:

- `https://accounts.google.com/o/oauth2/v2/auth`
- `https://oauth2.googleapis.com/token`
- `https://oauth2.googleapis.com/revoke`
- `https://openidconnect.googleapis.com/v1/userinfo`
- `https://www.googleapis.com/calendar/v3/calendars/primary/events`
- `https://gmail.googleapis.com/gmail/v1/users/me/messages/send`

All provider calls use a 15-second timeout, reject redirects, and cap response
bodies at 64 KiB. Access tokens, refresh tokens, client secrets, authorization
codes, raw provider errors, email contents, and event contents never enter logs,
audit metadata, client DTOs, URL query strings outside Google's authorization
request, or handoffs.

The OAuth client uses dedicated server variables:

- `GOOGLE_WORKSPACE_CLIENT_ID`
- `GOOGLE_WORKSPACE_CLIENT_SECRET`
- `GOOGLE_WORKSPACE_REDIRECT_URI`

These remain separate from Supabase sign-in provider configuration.

### Token exchange, identity, and storage

The initial token exchange must return:

- a Bearer access token;
- a refresh token;
- a positive bounded `expires_in` value;
- every exact required scope.

The adapter then calls OIDC UserInfo with the access token in the Authorization
header. It requires a non-empty stable `sub`, a syntactically valid email, and
`email_verified=true`.

Both integration rows store only encrypted `access_token` and `refresh_token`.
Safe columns store the Google subject, email, exact scopes, token expiration,
healthy status, actor, and connection timestamps. The two rows are upserted as
one array statement so the bundle cannot be half-connected.

### Refresh lifecycle

Provider operations and Tests obtain a valid access token through one shared
server-only helper:

1. Load both active organization rows.
2. Require the two rows to share the same Google subject, email, scope set,
   expiration, access token, and refresh token.
3. Reuse an access token only while it has more than 60 seconds remaining.
4. Otherwise exchange the refresh token at Google's fixed token endpoint.
5. Require a Bearer access token and the expected scopes if scopes are returned.
6. Atomically update encrypted credentials and expiration in both rows.
7. Record `token_refreshed` for both safe provider audit streams.

An invalid or rejected refresh marks both rows `reauth_required`, records only
the normalized error code, and never retries automatically. Transient failures
mark both rows degraded. Refresh tokens returned during refresh replace the old
token; omission preserves it.

### Read-only Test

Calendar Test obtains a valid token and performs a bounded `events.list` on the
primary calendar with `maxResults=1`, `singleEvents=true`, a current `timeMin`,
and no event-body persistence.

Gmail's `gmail.send` scope does not authorize any non-mutating Gmail resource
method. Gmail Test therefore validates the shared token through OIDC UserInfo,
verifies that the exact Gmail scope is present, and verifies the stored subject
and email. It does not send a synthetic message and does not request a broader
scope merely to make Test call Gmail.

Successful tests mark the whole bundle healthy. A provider failure marks the
whole bundle degraded or reauthorization-required because credentials are
shared.

### Disconnect

Disconnect loads the shared refresh token, sends one bounded revocation request,
and then clears credentials and disables both local rows in one database
statement regardless of remote cleanup outcome. This order prevents continued
local use if Google is unavailable. The action returns a safe warning when
remote revocation cannot be verified and records one disconnected audit event
per provider with only `remote_cleanup` status.

Google documents that revocation removes the grant's previously authorized
scopes, so a single-provider disconnect is intentionally not offered:
<https://developers.google.com/identity/protocols/oauth2/web-server#tokenrevoke>.

## Constrained Provider Operations

### Calendar appointment creation

`createGoogleCalendarAppointment` is server-only and accepts:

- summary: 1-200 Unicode characters;
- description: optional, at most 2,000 characters;
- location: optional, at most 500 characters;
- start and end: RFC 3339 timestamps with explicit offsets;
- time zone: a valid IANA zone, at most 100 characters;
- attendee: optional single syntactically valid email address.

The end must be after the start, duration may not exceed 24 hours, and the
start may not be more than one year in the past or two years in the future.
Only the authenticated user's `primary` calendar is allowed. Recurrence,
attachments, arbitrary extended properties, conference creation, reminders,
guest modification, and alternate calendar IDs are rejected.

When an attendee is present, Google receives `sendUpdates=all`; otherwise it
receives `sendUpdates=none`. Revora stores no event body. A successful audit
event contains only Google event ID, attendee presence, and duration minutes.

### Gmail plain-text send

`sendGoogleWorkspaceEmail` is server-only and accepts:

- exactly one syntactically valid recipient;
- subject: 1-200 characters;
- plain-text body: 1-20,000 characters.

Header CR/LF injection is rejected. The adapter creates a CRLF RFC 5322 message
with `To`, UTF-8 encoded `Subject`, `MIME-Version`, and
`Content-Type: text/plain; charset=UTF-8`, then sends its base64url form through
`users.messages.send` as `me`.

There is no caller-controlled From, Cc, Bcc, Reply-To, HTML, attachment, thread,
label, draft, or raw MIME input. Revora stores no recipient, subject, or body.
A successful audit event contains only the returned message ID and recipient
count `1`.

Both mutating functions make one provider request and do not automatically
retry ambiguous failures, preventing silent duplicate appointments or emails.
They normalize provider errors and update bundle health consistently.

## Authorization and Tenant Isolation

- Settings Connect, Test, and Disconnect re-authorize
  `integrations.manage` against the current active organization on every call.
- The callback re-authorizes the signed-in actor and validates the OAuth state
  against that same organization.
- Server-only provider operations require a caller-supplied organization ID
  from an already authorized server boundary; no client can provide credentials
  or a Google subject.
- Every connection lookup and mutation includes the organization ID and both
  fixed provider IDs.
- Safe client DTOs expose status, Google email, scopes, and timestamps only.
- Credential fields remain encrypted at rest and service-role-only.

## Error Model

Google responses map to the existing safe categories:

- 400 `invalid_grant` during refresh, 401, or invalid token:
  `REAUTH_REQUIRED` / `INVALID_CREDENTIALS`;
- 403 insufficient permission or API disabled: `CONFIGURATION_ERROR`;
- 429: `RATE_LIMITED`;
- 5xx: `PROVIDER_UNAVAILABLE`;
- timeout/network failure: `NETWORK_ERROR`;
- malformed, oversized, redirected, identity-mismatched, or scope-mismatched
  response: `INVALID_RESPONSE`.

Provider response bodies and exception details are not returned to the client.

## Verification

The phase adds a deterministic `test:google-workspace` contract suite covering:

- exact authorization origin, parameters, scopes, and state;
- token and UserInfo parsing, missing refresh token, bad identity, missing and
  extra scopes;
- timeout, redirect, body bound, and normalized errors;
- coordinated identity/credential expectations;
- refresh response rules;
- read-only Calendar Test request shape;
- Calendar input bounds and exact event request body;
- Gmail input bounds, CR/LF rejection, Unicode subject encoding, base64url MIME,
  one-recipient-only behavior, and exact send endpoint;
- disconnect semantics and no-secret safe metadata contracts.

The closure gate also runs all previous integration suites, lint, typecheck,
production build, `npm audit`, migration immutability hashes, diff checks, and a
credential/non-printing scan.

## Live Gates

Local completion is separate from live completion. Live OAuth and provider
mutations remain blocked until the user supplies or authorizes:

- a non-production Google Cloud project;
- enabled Calendar and Gmail APIs;
- configured OAuth consent screen/test users;
- exact OAuth client variables and redirect URI;
- an HTTPS reachable Revora callback origin;
- authorized application of pending migrations to the intended Supabase
  project;
- explicit test recipient and calendar timing for mutating E2E checks.

No credential, migration application, push, deployment, purchase, live email,
or live event creation is part of local implementation.
