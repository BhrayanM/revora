# Phase 14.6E Tally Integration Design

**Date:** 2026-08-21

**Status:** Approved for autonomous local implementation

**Scope:** One API-managed Tally form per Revora organization

## Objective

Add secure inbound Tally lead capture without requiring the user to copy or
paste webhook URLs or signing secrets. Revora discovers the user's forms,
suggests a lead-field mapping, creates the remote webhook, verifies every
submission, and creates at most one lead for each Tally event.

## Approved Decisions

1. Tally uses an API key entered by an authorized organization administrator.
2. Phase 14.6E supports one selected Tally form per Revora organization.
3. Revora discovers the form fields, proposes mappings for name, email, phone,
   company, and message, and requires confirmation before connecting.
4. The architecture stores the selected form and mapping in a shape that can
   support multiple forms in a later phase without changing the inbound event
   contract.
5. Revora creates and deletes the remote Tally webhook through the Tally API.
   The user does not manually transfer webhook URLs or secrets.
6. Existing migrations `00001` through `00033` remain immutable. Phase 14.6E
   creates migration `00034` for replay-safe event tracking changes only.

## Provider Contract

Revora uses only the HTTPS API origin `https://api.tally.so` with Bearer
authentication. Requests pin the documented `2025-02-01` API version using the
`tally-version` header so response shapes do not silently change with API-key
rotation.

Provider operations are constrained to:

- `GET /forms` to discover accessible forms.
- `GET /forms/{formId}` or `/forms/{formId}/questions` to inspect fields.
- `POST /webhooks` to create one `FORM_RESPONSE` subscription.
- `GET /webhooks` to verify that the stored webhook still exists and is active.
- `DELETE /webhooks/{webhookId}` during disconnect or rollback.

Provider calls use a fixed origin, redirects disabled, a 15-second timeout,
bounded response parsing, safe error codes, and no logging of request headers or
provider bodies. Revora never fetches historical submissions during this phase.

## Connection Flow

### Step 1: Discover forms

An administrator with `integrations.manage` enters a Tally API key. A dedicated
server action normalizes the key, calls the bounded forms endpoint, filters out
deleted forms, and returns only safe form IDs, names, status, and closed state.
The API key is never returned to the client or written to logs.

### Step 2: Inspect and map

After the administrator selects one form, Revora fetches its question metadata.
The mapping engine proposes:

- email from an email-type field first, then safe label aliases;
- phone from a phone-type field first, then safe label aliases;
- name, company, and message from compatible text fields and normalized labels.

The administrator may correct every suggestion. The configuration requires a
mapped email or phone field. Name, company, and message are optional. Only field
IDs, labels, supported scalar types, and the final mapping reach the browser.

### Step 3: Connect

On confirmation, the server re-authorizes `integrations.manage`, revalidates the
form and mapping against Tally, generates a random routing token and a separate
random signing secret, and creates the remote webhook. The public endpoint is:

`/api/integrations/tally/webhook/{routingToken}`

The routing token is stored only as a SHA-256 hash in safe connection config.
The Tally API key and signing secret are stored only inside the encrypted
credentials object. Safe connection config stores the form ID/name, remote
webhook ID, confirmed field mapping, and routing-token hash.

The connection is persisted only after Tally confirms webhook creation. If
local persistence fails, Revora attempts a bounded remote webhook deletion. An
orphaned remote webhook remains harmless because no active local routing-token
record exists.

## Inbound Request Flow

The route performs these steps in order:

1. Require `POST` with `application/json` and reject a declared or actual body
   larger than 1 MiB.
2. Hash the routing token and load exactly one active Tally connection. Unknown
   tokens receive a uniform not-found response without tenant details.
3. Read the exact request body, require `Tally-Signature`, calculate
   HMAC-SHA256 with the decrypted signing secret, encode it as Base64, and use a
   timing-safe comparison before parsing or persisting provider data.
4. Parse a bounded `FORM_RESPONSE` payload and require the configured form ID,
   non-empty event ID, submission ID, and supported scalar mapped fields.
5. Hash the payload and claim the event in the organization-scoped inbound
   event ledger. A previously completed event returns success without creating
   a second lead. A conflicting payload for the same event ID fails closed.
6. Resolve the organization's first workspace, default pipeline, and first
   stage using the existing CRM convention.
7. Convert only mapped values to the existing normalized lead contract. Require
   at least one non-empty email or phone value. Store only safe Tally metadata:
   form ID/name, submission ID, event ID, and ingestion timestamp.
8. Insert the lead with source `other` and source external ID
   `tally:{formId}:{submissionId}`. The existing unique lead index is a second
   idempotency boundary.
9. Mark the event processed, link the lead, dispatch the existing outbound
   `lead.created` event, and return a small 2xx response within Tally's timeout.

Raw Tally payloads, preview URLs, PDF URLs, file URLs, signature images,
unmapped answers, API keys, and signing secrets are never stored in the event
ledger, lead metadata, audit metadata, or logs.

## Database Design

Migration `00034` reuses `integration_webhook_events` rather than creating a
provider-specific event table:

- replace the global `(provider, external_event_id)` uniqueness boundary with
  `(organization_id, provider, external_event_id)`;
- add nullable `lead_id` with `ON DELETE SET NULL`;
- add `attempt_count`, `last_attempt_at`, and supporting indexes;
- preserve existing status values and historical rows;
- add only the audit event types needed for inbound receipt, duplicate,
  rejection, and lead capture;
- ensure RLS remains enabled and mutations remain server-only.

Because Supabase no longer guarantees automatic Data API exposure for new
tables, this phase avoids a new table. Existing grants and policies are
reviewed explicitly; authenticated clients receive no direct mutation policy.

Event claiming uses insert-on-conflict plus an optimistic retry transition for
failed or stale `received` rows. Tally's documented first retry occurs after
five minutes, so a short processing lease lets a crashed request recover while
concurrent duplicates remain no-ops. The existing lead uniqueness constraint
prevents a second lead even if processing is retried after an ambiguous result.

## Test and Disconnect

`Test` performs read-only API checks: it verifies the selected form and finds
the stored webhook in the paginated webhook list. It creates no submission and
sends no synthetic lead.

`Disconnect` first attempts to delete the remote webhook. Regardless of a
provider cleanup failure, Revora disables the local endpoint and clears local
credentials so future deliveries cannot create leads. A safe warning and audit
code record when manual remote cleanup may still be necessary.

## Error Handling

- Invalid credentials or revoked access: `INVALID_CREDENTIALS` or
  `REAUTH_REQUIRED`.
- Rate limiting: `RATE_LIMITED` with no provider body returned.
- Timeout/network/provider 5xx: `NETWORK_ERROR` or `PROVIDER_UNAVAILABLE`.
- Malformed provider success: `INVALID_RESPONSE`.
- Invalid signature: `INVALID_SIGNATURE`, no payload persistence.
- Wrong form or unsupported event: rejected or ignored without lead creation.
- Duplicate event with identical payload: idempotent 2xx.
- Duplicate event with a different payload hash: fail closed and audit a safe
  conflict code.
- Transient persistence failure: 5xx so Tally retries according to its delivery
  schedule.

Provider and persistence failures never expose credentials, raw answers,
provider bodies, SQL details, stack traces, or another organization's state.

## Security Properties

- Every discovery, connect, test, and disconnect action re-authorizes the
  current organization and `integrations.manage` permission.
- API keys and signing secrets are encrypted at rest and server-only.
- Routing tokens have at least 256 bits of entropy and are hashed at rest.
- Signature verification precedes JSON parsing and database writes.
- Signature and hash comparisons use constant-time primitives where applicable.
- The configured form ID must match the signed event form ID.
- Event uniqueness and all database lookups include organization scope.
- The public route uses bounded bodies, bounded parsing, fixed provider origins,
  rate limiting, safe responses, and no redirects.
- Client-safe connection DTOs never include API keys, signing secrets, routing
  tokens, webhook URLs, or raw provider responses.
- Phase 14.6D Slack and Twilio contracts remain unchanged.

## Test Strategy

Implementation follows red-green-refactor with deterministic provider doubles
and hand-derived HMAC fixtures.

Tests cover:

- API-key normalization and secret-safe errors;
- fixed Tally origin, Bearer auth, pinned version, timeout, no redirects, and
  response-size limits;
- form discovery pagination and safe DTOs;
- field detection, mapping suggestions, validation, and unsupported values;
- remote webhook creation, local persistence, and rollback cleanup;
- exact raw-body HMAC acceptance plus altered body/signature rejection;
- missing signature, wrong form, wrong event type, oversized body, and malformed
  JSON;
- valid lead creation with only mapped fields retained;
- simultaneous duplicate delivery, completed replay, failed retry, stale claim
  recovery, and payload-hash conflict;
- existing lead uniqueness as a second deduplication boundary;
- cross-tenant routing-token, event, connection, test, and disconnect failures;
- safe test and disconnect behavior;
- regression coverage for all Phase 14.6B-14.6D providers.

The phase gate includes the Tally verification suite, integration and
communication regressions, lint, typecheck, production build, dependency audit,
SQL/migration validation, linked migration comparison, secret scan, and
`git diff --check`.

## Acceptance Criteria

1. An authorized administrator can enter a Tally API key, select one form,
   confirm a suggested lead mapping, and connect without manually configuring a
   webhook.
2. A valid signed submission from the selected form creates exactly one lead.
3. Replays, concurrent duplicates, wrong forms, invalid signatures, oversized
   bodies, and cross-tenant attempts create no additional lead.
4. Test is read-only and Disconnect disables local ingestion even if remote
   cleanup fails.
5. No raw form payload or credential reaches client DTOs, logs, audit metadata,
   commits, or documentation.
6. Migrations `00001` through `00033` remain byte-for-byte unchanged.

## Out of Scope

- Multiple simultaneous forms per organization.
- Historical submission import or polling.
- Creating or editing Tally forms.
- Arbitrary answer storage, file/PDF retrieval, or electronic-signature
  storage.
- Conditional field transformations beyond the confirmed scalar mapping.
- Production deployment, push, purchases, or paid provider operations.
