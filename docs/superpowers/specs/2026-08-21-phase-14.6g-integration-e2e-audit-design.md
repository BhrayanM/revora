# Phase 14.6G Complete Integration E2E Audit Design

**Date:** 2026-08-21  
**Status:** Implementation-ready  
**Scope:** Phase 14.6A-14.6F integration system

## Goal

Produce one repeatable, evidence-backed integration gate covering every Revora
provider and the shared security/reliability infrastructure. The audit must
distinguish deterministic local PASS evidence from live gates that remain
blocked by credentials, HTTPS origins, linked migrations, or explicit mutation
authorization.

## Provider Inventory

The audit covers exactly:

- CRM: HubSpot, GoHighLevel;
- automation: n8n, Zapier, Make;
- communication: Slack, Twilio infrastructure;
- lead capture: Tally;
- Google Workspace: Google Calendar, Gmail.

Twilio SMS/WhatsApp/voice/number purchase and all other deferred product work
remain out of scope.

## Audit Layers

### 1. Catalog and schema continuity

- Catalog IDs, database provider allowlist, categories, auth types, and required
  scopes agree.
- Migrations `00001`-`00035` match the completed 14.6F checkpoint as committed
  Git content and as normalized working-tree content.
- Provider uniqueness remains organization-scoped.
- Webhook event uniqueness remains organization/provider/external-event scoped.
- No new migration is expected in 14.6G; a schema change requires a separately
  justified forward-only `00036`.

### 2. Authorization and tenant isolation

- Every Settings read uses `integrations.read`.
- Every Connect, Test, Disconnect, discovery, or credential save uses
  `integrations.manage` at execution time.
- OAuth state is random, hashed, expiring, single-use, provider-bound, and
  organization-bound.
- PKCE verifier material is encrypted while temporarily persisted and decrypted
  only after successful state validation.
- Every server repository/provider query includes organization scope, except a
  public webhook routing lookup whose unguessable token is hashed and resolves
  exactly one active connection.
- Client-safe DTOs never contain credentials, config secrets, webhook URLs,
  refresh/access tokens, API keys, auth tokens, signing secrets, or PKCE values.

### 3. Network and credential safety

- OAuth/API origins are fixed by adapters.
- User-supplied webhook URLs pass HTTPS, DNS/IP, private-network, credential,
  redirect, timeout, and response-size controls.
- Provider credentials are encrypted before persistence and cleared on local
  disconnect.
- Audit metadata and user-facing errors contain normalized codes and safe IDs,
  never credential values or provider response bodies.
- No active provider credential pattern or nonblank provider secret assignment
  exists in changed/tracked artifacts.

### 4. Retry and idempotency

- Automation delivery uses durable executions and bounded retries without
  rolling back lead persistence.
- Tally uses tenant-scoped event claims plus lead source uniqueness and safely
  handles duplicate, conflict, failed, in-progress, and stale-recovery paths.
- Slack HOT alerts remain post-persistence and exact-HOT only.
- Google Calendar/Gmail mutations make one attempt and never automatically
  retry an ambiguous provider result.
- Twilio remains read-only and has no mutating operation to retry.

### 5. Provider lifecycle regression

The aggregate local command runs the completed deterministic suites for:

- n8n/Zapier/Make;
- Slack/Twilio;
- Tally;
- Google Calendar/Gmail;
- the new cross-provider static audit.

It also validates lint, strict types, production build, dependency audit,
format/diff, route generation, and documented environment/migration state.

### 6. Live-vs-blocked evidence

The audit may inspect only presence/status of configured variables and safe
connection metadata. It must not print secret values. It may perform a live
provider Test only when credentials already exist, the intended non-production
organization is authorized, and the Test is non-mutating or its mutation was
explicitly approved.

Without those prerequisites, the provider is `BLOCKED_CREDENTIALS` or
`PENDING_EXTERNAL_AUTHORIZATION`, not failed and not passed. The audit never
links/applies a Supabase project, pushes, deploys, purchases, sends a live
message, or creates a live event on its own.

## Deterministic Audit Harness

Add `scripts/verify-integration-e2e-audit.mjs` and
`npm.cmd run test:integration-e2e`.

The static harness reads source and migration artifacts without credentials or
network access. It verifies:

- exact provider inventory and no broad Google scopes;
- safe connection DTO boundaries;
- generic action guards for OAuth/specialized providers;
- organization predicates in connection, webhook, execution, OAuth-state, and
  provider mapping repositories;
- encrypted credential and PKCE persistence paths;
- OAuth-state validation order and single-use consumption;
- public webhook signature/token/body-limit contracts;
- automation retry/idempotency and Google no-retry source contracts;
- all migration names/order and immutable baseline comparison;
- no provider adapter imported by client components;
- documentation contains one explicit live status for every provider.

The aggregate package command runs the four established suites and this audit
in a stable order. It is deterministic and performs no live provider mutation.

## Confirmed Initial Finding

Initial inventory found that `storePKCEVerifier` writes the verifier directly to
`pkce_verifier_encrypted`, and `validateOAuthState` returns it directly. This is
inconsistent with the encrypted-at-rest contract. The audit must first fail on
this condition, then the minimal remediation must:

1. encrypt the verifier with the integration encryption helper before storage;
2. decrypt only after state, expiration, organization, provider, and single-use
   checks succeed;
3. fail closed when the stored value is malformed or cannot be decrypted;
4. never log or expose the verifier;
5. require no migration because the column is already text and existing OAuth
   states expire after ten minutes.

No other finding is considered confirmed until a failing deterministic check
or concrete source-to-sink trace demonstrates it.

## Outputs

- `docs/audits/PHASE_14.6G_INTEGRATION_E2E_AUDIT_2026-08-21.md` with provider

- Phase 14.6G completion handoff and one independent local closure commit;
- exact transition to Phase 14.7 Product UX Completion.

## Completion Criteria

14.6G is locally complete only when:

1. the aggregate audit and every constituent suite pass freshly;
2. all confirmed high/medium integration findings are remediated or explicitly
   blocked by an external decision;
3. lint, typecheck, default production build, and `npm audit` pass;
4. migrations `00001`-`00035` remain unchanged and no unauthorized migration is
   applied;
5. secret/control/temp scans are clean;
6. every provider has an honest local and live status;
7. the repository is clean on local `master`, with no push or deployment.
