# Phase 14.6D Slack and Twilio Design

**Date:** 2026-08-20

**Status:** Approved for specification

**Scope:** Slack production flow plus Twilio infrastructure only

## Objective

Complete the communication-provider phase without activating paid Twilio
messaging. Slack becomes a usable, tenant-isolated integration for HOT-lead
alerts. Twilio gains secure credential handling, read-only connection tests,
normalized errors, and reusable request-signature verification, but sends no
SMS and places no calls.

## Decisions

1. Slack uses OAuth v2 with the `incoming-webhook` bot scope. The Slack channel
   picker in the installation flow selects the destination channel.
2. Slack stores the OAuth access token and incoming webhook URL only in the
   encrypted server-side credentials object. Safe workspace and channel labels
   may be stored as connection metadata.
3. A successful HOT qualification sends one Slack alert. WARM and COLD
   qualifications do not send alerts.
4. Slack delivery failure does not roll back a successfully persisted AI
   qualification. It updates integration health and returns no secret or raw
   provider response to the client.
5. Twilio accepts an Account SID, Auth Token, and optional source phone number.
   It validates the account through a read-only Twilio API request. If a source
   number is supplied, the number must be E.164 and belong to that account.
6. Twilio does not send SMS, WhatsApp messages, or voice calls in this phase.
7. Existing integration tables and encrypted credential storage are sufficient.
   Phase 14.6D creates no migration unless implementation proves a schema gap;
   any such gap requires a new migration after `00033`, never an edit to an
   earlier migration.

## Existing Architecture Reused

- `integration_oauth_states` supplies hashed, expiring, single-use OAuth state
  bound to organization and provider.
- `integrations` stores lifecycle state, health, encrypted credentials, safe
  external account metadata, scopes, and timestamps.
- `integration_audit_events` records connection lifecycle events without
  credentials.
- `saveConnection`, `getDecryptedCredentials`, `disconnectConnection`,
  `markConnectionHealthy`, and `markConnectionError` remain the persistence
  boundary.
- `src/lib/notifications/slack.ts` remains the Slack Block Kit renderer and
  delivery primitive after its validation and transport behavior are hardened.

## Slack Components

### OAuth adapter

Create `src/lib/integrations/adapters/slack.ts` with these responsibilities:

- Build the Slack OAuth v2 authorization URL using `SLACK_CLIENT_ID`,
  `SLACK_REDIRECT_URI`, the `incoming-webhook` scope, and an organization-bound
  OAuth state.
- Exchange the temporary code at `https://slack.com/api/oauth.v2.access` using
  `SLACK_CLIENT_ID` and `SLACK_CLIENT_SECRET`.
- Require Slack's JSON response to have `ok: true`, a bot access token, team
  identity, and an `incoming_webhook` object with URL and channel identity.
- Persist encrypted `access_token` and `webhook_url`; store team ID/name and
  channel ID/name only as safe metadata.
- Test the connection with Slack `auth.test`. A user-initiated UI test also
  sends one clearly labeled integration-test message through the stored incoming
  webhook.
- Normalize 401/invalid-auth to `INVALID_CREDENTIALS`, 429 to `RATE_LIMITED`,
  provider 5xx to `PROVIDER_UNAVAILABLE`, timeouts to `NETWORK_ERROR`, and
  malformed success payloads to `INVALID_RESPONSE`.
- Disconnect by clearing credentials and connection metadata through the shared
  connection service.

### OAuth callback route

Create `src/app/api/integrations/slack/callback/route.ts` following the existing
HubSpot callback security model:

- Require the authenticated user and current organization.
- Reject missing code/state and Slack-declared OAuth errors.
- Validate the single-use state against provider `slack` and the current
  organization before token exchange.
- Redirect to `/settings?tab=integrations` with a safe success or error marker.
- Never include provider response bodies, tokens, webhook URLs, or stack traces
  in the redirect or logs.

### Settings actions and UI

- Add `startSlackOAuth`, `testSlack`, and `disconnectSlack` server actions with
  `integrations.manage` authorization.
- Make Slack's Connect button start OAuth instead of rendering the generic
  webhook form.
- Display only connection status, health, workspace name, and channel name.
- Keep all credentials and webhook URLs outside client-safe DTOs.

### HOT-lead notification flow

Create a focused server-side orchestrator that receives the organization, lead,
and validated qualification result:

1. Return immediately unless the deterministic temperature is `HOT`.
2. Load the active Slack connection for that organization only.
3. Build the alert from the persisted lead and validated qualification result.
4. Deliver through the stored incoming webhook with HTTPS, exact
   `hooks.slack.com` origin validation, redirects disabled, a 15-second timeout,
   and a bounded response body.
5. Mark the connection healthy on success or degraded/reauth-required with a
   safe code on failure.

Both interactive and service-level qualification paths call the same
orchestrator after the lead qualification has been persisted successfully.
Slack delivery is awaited for deterministic testing, but delivery failure is
non-fatal to qualification.

## Twilio Infrastructure Components

Create `src/lib/integrations/adapters/twilio.ts` with no send operation.

### Credential normalization

- Require Account SID format `AC` followed by 32 hexadecimal characters.
- Require a non-empty Auth Token and never log it.
- Normalize an optional source phone number to E.164; reject other formats.
- Store normalized values only through the encrypted connection service.

### Read-only connection validation

- Authenticate over HTTPS using HTTP Basic authentication against the Twilio
  2010-04-01 REST API.
- Fetch the configured account and require the returned SID to match exactly.
- If a source number is present, query the account's IncomingPhoneNumbers
  collection and require an exact E.164 match.
- Store only the account SID and friendly name as safe external metadata.
- Update health using normalized safe errors. No validation request may create,
  update, buy, call, or message any Twilio resource.

### Request-signature verification primitive

Provide a pure, server-only verifier for future Twilio callbacks:

- Accept the exact public request URL, form parameters, received
  `X-Twilio-Signature`, and decrypted Auth Token.
- Reproduce Twilio's documented HMAC-SHA1 signing input and compare the Base64
  signature in constant time.
- Reject missing signatures, malformed inputs, and unequal-length values without
  throwing provider secrets.
- Do not expose a public Twilio webhook route in this phase because no Twilio
  messaging or voice workflow is active.

### Settings actions and UI

- Add dedicated `saveTwilioIntegration`, `testTwilio`, and `disconnectTwilio`
  actions guarded by `integrations.manage`.
- Replace the generic save path for Twilio so credentials are normalized and
  remotely verified before persistence.
- Keep the existing Account SID, Auth Token, and source-number form, with the
  source number explicitly marked optional and no send controls.

## Security Properties

- Every connection read/write is scoped by the authenticated organization.
- OAuth state is random, hashed at rest, expires after ten minutes, is
  single-use, and is bound to Slack plus the organization.
- Slack and Twilio credentials remain server-only and encrypted at rest.
- Slack webhook delivery permits only the exact HTTPS Slack webhook origin and
  never follows redirects.
- Provider calls use timeouts and bounded response parsing.
- Timing-safe comparisons protect request signatures.
- Audit metadata contains only provider, event type, safe status/error code,
  HTTP status when useful, and actor profile ID.
- User-facing errors use the existing safe integration error catalog.
- No Twilio operation in 14.6D can incur messaging, calling, number-purchase, or
  other resource-mutation charges.

## Test Strategy

Implementation follows red-green-refactor. Tests exercise exported behavior
through deterministic fetch doubles and hand-derived fixtures.

### Slack tests

- Authorization URL contains the expected client, redirect, scope, and opaque
  state without secrets.
- State mismatch, expiration, replay, wrong provider, and cross-tenant use fail.
- OAuth exchange rejects Slack `ok: false`, missing incoming webhook data, and
  malformed account metadata.
- Successful exchange stores encrypted secrets and only safe account/channel
  metadata.
- Connection test handles success, invalid auth, rate limiting, provider 5xx,
  timeout, and malformed JSON.
- Slack webhook URL validation blocks HTTP, lookalike hosts, credentials in URLs,
  nonstandard ports, redirects, oversized responses, and local/private targets.
- HOT produces exactly one escaped alert; WARM and COLD produce none.
- A Slack failure leaves the persisted qualification successful and updates
  integration health with a safe code.
- Tenant B cannot use Tenant A's Slack connection.

### Twilio tests

- Account SID, Auth Token, and E.164 validation accept valid fixtures and reject
  malformed values.
- Read-only account validation uses the exact account endpoint and Basic auth.
- Optional phone-number ownership validation succeeds only on an exact match.
- 401, 403, 429, 5xx, timeout, and malformed responses map to safe errors.
- Successful persistence encrypts credentials and returns only safe metadata.
- The signature verifier accepts an official-style hand-derived fixture and
  rejects altered URL, parameters, signature, and token.
- No adapter export or UI action can send a Twilio message or call.
- Tenant B cannot read or test Tenant A's Twilio connection.

### Phase gate

- Provider-focused verification script passes.
- Existing `test:integrations` regression suite passes.
- `npm run lint`, `npm run typecheck`, `npm run build`, and `npm audit` pass.
- `git diff --check` passes.
- The linked Supabase migration list remains synchronized through `00033` when
  no schema change is required.
- Modified and untracked content passes the repository secret scan.
- Slack live E2E is performed only when an existing Slack app/workspace and
  credentials are available. Twilio live messaging E2E is explicitly excluded.

## Acceptance Criteria

1. An authorized Revora administrator can connect Slack through OAuth, see safe
   workspace/channel metadata, test it, and disconnect it.
2. A successful HOT qualification sends one Slack alert; WARM/COLD send none.
3. Slack failures never corrupt or roll back lead qualification.
4. An authorized administrator can securely save and read-only test Twilio
   credentials without sending or purchasing anything.
5. Slack and Twilio credentials never reach client DTOs, logs, audit metadata,
   commits, or handoff documents.
6. Cross-tenant connection use fails closed for both providers.
7. Phase 14.6C behavior and migrations `00001` through `00033` remain intact.

## Out of Scope

- Sending Twilio SMS, WhatsApp, or voice calls.
- Buying or configuring Twilio phone numbers.
- Public Twilio webhook endpoints or status callbacks.
- Slack slash commands, interactive components, event subscriptions, or custom
  channel selection outside Slack's OAuth installer.
- Background polling for provider health.
- Production deployment or push to a Git remote.
